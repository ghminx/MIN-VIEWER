# Android 엔진 연동 시험

기준일: 2026-11-09  
상태: 개발용 PoC. 완성된 문서 뷰어나 배포용 APK가 아님.

## 환경과 빌드

- 앱: Kotlin, Android Gradle Plugin 8.9.3, Gradle 8.11.1, compile SDK 35. 최소 SDK는 사용자 결정에 따라 29로 변경함.
- 시험 환경: Windows, JDK 23, Android SDK 35, Android 15 x86_64 에뮬레이터.
- 로컬 SDK와 Gradle, 시험 패키지 및 공개 표본은 `.research`에 설치함. 해당 경로와 빌드 산출물은 Git 추적에서 제외함.
- Google SDK 명령줄 도구 다운로드 파일의 SHA-256을 공식 다운로드 페이지의 값과 대조함. SDK 관리자의 라이선스 절차를 실행함.
- 한글은 `@rhwp/core@0.9.0`, 기존 DOCX·XLSX는 `@opendocument/odr-core@7.7.0`, 기존 PPTX는 `@office-kit/pptx@0.28.0`과 `@office-kit/pptx-preview@0.21.0`을 WebView의 로컬 자산으로 실행함. 별도 LibreOfficeKit 26.2.6.3 ARM64 시험 경로를 추가함.

프로젝트 루트에서 엔진 패키지 설치 및 디버그 빌드 예시임. 먼저 아래 수정 한글 엔진과 LibreOffice ARM64 APK를 지정 위치에 준비해야 함.

```powershell
npm.cmd install --prefix .research/engine-poc --ignore-scripts --no-audit --no-fund @rhwp/core@0.9.0 @opendocument/odr-core@7.7.0
npm.cmd install --prefix .research/office-alternatives --ignore-scripts --no-audit --no-fund @office-kit/pptx@0.28.0 @office-kit/pptx-preview@0.21.0 esbuild@0.28.2
Copy-Item tools/pptx-entry.js .research/office-alternatives/entry.js
.research/office-alternatives/node_modules/.bin/esbuild.cmd .research/office-alternatives/entry.js --bundle --format=esm --platform=browser --minify --outfile=.research/office-alternatives/pptx-viewer.js
$env:ANDROID_HOME = 'Android SDK 경로'
.\gradlew.bat assembleDebug
```

SDK 플랫폼 35와 build-tools 35.0.0 및 JDK가 필요함. 위 명령은 개발 의존성 다운로드를 포함하며, 생성된 앱이 실행 중 문서를 서버로 전송하는 방식은 아님. 배포 전 엔진·글꼴·전이 의존성 고지와 빌드 재현성 검토가 필요함.

### 수정된 한글 엔진 준비

- rhwp `v0.9.0` 커밋 `c9095c5f67632e6721e800ccc7fb43ea49d26682`에 [차트 수정 패치](../patches/rhwp-0.9.0-chart.patch)를 적용함. 엔진은 MIT 라이선스이며 원본 라이선스와 제공된 의존성 고지를 앱에 포함함.
- Rust 1.93.1의 `wasm32-unknown-unknown` 대상과 `wasm-pack` 0.15.0으로 빌드함. 아래 예시는 WSL의 프로젝트 루트에서 실행하며, 첫 줄은 해당 경로에 엔진 소스가 없는 경우에만 실행함.

```sh
git clone --depth 1 --branch v0.9.0 https://github.com/edwardkim/rhwp.git .research/rhwp-090
git -C .research/rhwp-090 apply ../../patches/rhwp-0.9.0-chart.patch
cd .research/rhwp-090
wasm-pack build --target web --release --no-opt --out-dir ../rhwp-patched
cd ../..
```

- 앱 빌드는 `.research/rhwp-patched/rhwp.js`와 `rhwp_bg.wasm`을 사용하며 누락 시 실패함. 아래 선택적 최적화에는 Binaryen `wasm-opt` 133과 원본 WASM 기능 집합을 사용함. 최적화 전후 출력을 비교한 뒤 앱 빌드에 반영함.

```sh
wasm-opt .research/rhwp-patched/rhwp_bg.wasm -Oz \
  --enable-mutable-globals --enable-nontrapping-float-to-int --enable-bulk-memory \
  --enable-sign-ext --enable-reference-types --enable-multivalue \
  --enable-bulk-memory-opt --enable-call-indirect-overlong \
  -o .research/rhwp-patched/rhwp-optimized.wasm
mv .research/rhwp-patched/rhwp-optimized.wasm .research/rhwp-patched/rhwp_bg.wasm
```

### LibreOffice ARM64 산출물 준비

- Ubuntu 24.04 WSL, JDK 17, Android SDK 35, NDK 29.0.14206865 및 LibreOffice Android 빌드 의존성을 사용함. [LibreOffice 공식 교차 빌드 설명](https://github.com/LibreOffice/core/blob/libreoffice-26.2.6.3/README.cross) 및 [F-Droid 빌드 설정](https://gitlab.com/fdroid/fdroiddata/-/blob/master/metadata/org.documentfoundation.libreoffice.yml)을 참고함.
- LibreOffice 태그 `libreoffice-26.2.6.3`, 커밋 `8221e31b3ac356a1623c672912a3d2b492f7e3d1`을 사용함. Linux의 소스 디렉터리에서 SDK와 NDK 경로를 실제 값으로 대체해 다음 순서로 빌드함.
- CFB 버전 4 읽기를 위해 [엔진 패치](../patches/libreoffice-26.2-cfb4-read.patch)를 LibreOffice 소스 루트에서 적용한 후 빌드함. 원본 소스와 수정 사항을 함께 제공해야 함.

```sh
git apply /프로젝트_경로/patches/libreoffice-26.2-cfb4-read.patch
./autogen.sh --enable-release-build --with-vendor=MINVIEWER \
  --with-android-package-name=org.minviewer.app \
  --with-android-ndk=NDK_29_경로 --with-android-sdk=LINUX_SDK_경로 \
  --with-distro=LibreOfficeAndroidAarch64
make fetch
make PARALLELISM=8 -j8
```

- 생성된 `android/source/build/outputs/apk/strippedUI/release/LibreOfficeViewer-strippedUI-release-unsigned.apk`를 프로젝트의 `.research/office-alternatives/libreoffice-built-arm64-unsigned.apk`로 복사함. 앱 Gradle 작업이 이 APK의 ARM64 네이티브 라이브러리와 자산을 추출함.
- 본 앱에 포함된 `org.libreoffice.kit` JNI 바인딩은 위 LibreOffice 태그의 MPL 2.0 소스임. `LibreOfficeKit.java`에서 표준 출력·오류 로그 전환과 앱 내부 경로 로그를 제거하고 엔진 전용 캐시 경로를 지정함. 외부 배포 전 실제 바이너리·전이 의존성·글꼴의 고지 및 소스 제공 조건 확인이 필요함.

## APK와 권한

- 디버그 APK: LibreOfficeKit 포함 전 18,013,520바이트, ARM64 시험 엔진 포함 후 정리 빌드 기준 105,967,562바이트임. 두 값은 릴리스 APK 또는 설치 후 용량이 아님.
- Android Gradle 빌드에서 네이티브 라이브러리의 추가 strip을 수행하지 못해 기존 바이너리를 그대로 패키징한다는 경고가 발생함. 추가 strip 효과와 호환성은 미검증 상태임.
- APK 내부 압축 크기: rhwp WASM 11,252,843바이트, OpenDocument.core WASM 2,571,439바이트. 두 엔진 외 UI·런타임·자산도 총 APK에 포함됨.
- `aapt dump permissions` 결과 선언된 사용 권한 없음. 실제 네트워크 차단 및 비행기 모드 시험은 미실시 상태임.

### 공개 Office 모의 문서와 기준 PDF 비교

- [office2pdf 업무 문서 표본](https://github.com/developer0hye/office2pdf/tree/main/tests/golden_mocks/business)은 Microsoft Office에서 출력한 기준 PDF를 함께 제공함. 사용자 실문서가 아닌 공개 모의 문서임.
- OpenDocument.core 7.7.0에서는 한국어 PPTX의 두 번째 슬라이드에 있는 막대그래프 이미지가 표시되지 않았음. 같은 버전의 [PPTX 구현 문서](https://github.com/opendocument-app/OpenDocument.core/blob/v7.7.0/src/odr/internal/ooxml/presentation/README.md)는 이미지 지원을 미완료로 표시함.
- `office-kit` 시험 경로는 같은 파일의 이미지 요소를 SVG로 출력하며 Android 15 에뮬레이터에서도 그래프가 표시됨. 다만 기준 PDF와 달리 제목이 가운데에 표시됨. 글꼴과 복잡한 도형·차트의 전반적인 품질은 미확인 상태임.
- F-Droid의 LibreOffice Viewer 26.2.6.3 x86_64 별도 앱은 같은 에뮬레이터에서 그래프와 왼쪽 제목을 표시함. 한국어 DOCX 한 장은 PDF와 같은 페이지 형태로 표시되고 XLSX는 시트 일부가 표시됨. XLSX 전체 서식과 수식은 미검증 상태임. 해당 APK는 94,772,975바이트였으며, MIN VIEWER에 엔진을 포함한 크기가 아님. [F-Droid 배포 정보](https://f-droid.org/packages/org.documentfoundation.libreoffice/)
- 한국어 DOCX의 제목과 본문은 보였으나 기준 PDF와 달리 좁은 화면에 맞춰 줄바꿈되어 첫 화면만으로 원본 한 페이지 전체를 비교할 수 없었음.
- 한국어 XLSX는 표와 일부 값이 보였으나 가로 영역이 화면을 초과함. 스크롤·전체 값과 서식의 일치 여부는 아직 검증하지 않음.
- PPTX에서 주요 내용의 누락이 관찰되었으므로 OpenDocument.core를 Office의 최종 엔진으로 확정하지 않음. LibreOfficeKit을 MIN VIEWER의 별도 시험 경로로 연결했으며, 다양한 문서와 실기기 비교 전 최종 결정은 미완료 상태임.

## 초기 시험 범위와 남은 작업

아래 항목은 초기 시험 시점의 기록임. 이후 구현 상태는 문서 마지막의 추가 시험 결과를 기준으로 확인함.

- 파일 선택기로 문서를 읽고, HWP/HWPX 또는 Office 엔진을 확장자 기준으로 선택해 단일 페이지·시트·슬라이드를 표시함.
- 좁은 창에서 목록을 열면 문서 영역 대신 목록을 표시하고, 840dp 이상에서는 목록과 문서를 나란히 표시함. 번호 목록만 제공하며 썸네일은 미구현 상태임.
- 창 재생성 시 선택한 URI, 페이지 번호 및 목록 열림 상태를 복원하도록 시도함. 화면 확대 상태와 사용자 보기 방식은 아직 복원하지 않음.
- PDF·CSV, 외부 앱 열기·공유, 연속 스크롤·두쪽 보기, 슬라이드 전체 썸네일, 검색 및 완전한 접근성은 미구현 상태임.
- 파일 전달은 SAF 스트림을 앱 내부의 임의 토큰 URL로 연결해 Android 측 `readBytes` 및 Base64 복제를 제거함. WebView의 `arrayBuffer`와 엔진이 전체 문서를 메모리로 읽으므로 대용량 문제가 완전히 해결된 것은 아님.
- 약 25.36MB 합성 PPTX를 열고 3개 슬라이드를 인식함. 원본에 표시하지 않는 큰 PNG를 추가한 전송 시험이며 큰 이미지 렌더링·다수 페이지·실기기 메모리 검증은 아님.
- 형식 판별의 전체 변형, 오류 처리, 사용자의 실제 문서, 시트 탭 및 보안 경계 강화가 필요함.
- Office HTML은 스크립트를 허용하지 않는 sandbox iframe에 표시함. 외부 주소 차단을 위한 WebView 요청 검사와 CSP를 추가했으나, 보안 검토와 실제 네트워크 검증은 미완료 상태임.
- 최종 엔진 선택은 실제 Office 복잡 문서, HWP/HWPX 표·이미지 및 글꼴, 실기기 성능·크기 비교 이후로 보류함.

## LibreOfficeKit ARM64 준비 및 자원 정리 시험

- 2026-11-09 기준 Ubuntu 24.04 WSL에 빌드 도구와 JDK 17을 설치함. Google Linux SDK 도구의 SHA-256을 공식 게시값과 대조하고 Android SDK 35 및 NDK 29.0.14206865를 설치함.
- LibreOffice 26.2.6.3 소스 커밋 `8221e31b3ac356a1623c672912a3d2b492f7e3d1`에서 `LibreOfficeAndroidAarch64` 구성과 소스 빌드가 성공함. 서명되지 않은 원본 Viewer ARM64 APK는 87,583,534바이트임.
- 문서 전환 시 이전 파일 읽기를 취소하고, 지원하지 않는 형식의 파일은 내용을 읽기 전에 거부하도록 수정함. HWP 페이지 수 또는 OpenDocument.core 화면 목록을 읽는 도중 실패할 때 열린 엔진 자원을 해제함. 지원 형식의 파일 전체를 WebView에서 읽는 구조는 유지됨.
- Node 시험 10개와 `clean assembleDebug`가 성공함. 시험 중 PPTX 이미지는 공개 표본에 의존하므로 별도 엔진과의 완전한 표시 품질 비교가 아님.
- Android 15 x86_64 에뮬레이터에서 수정된 앱이 공개 HWP를 35쪽으로 열고, 공개 PPTX 및 약 25.36MB 합성 PPTX를 열었으며 두 번째 슬라이드의 막대그래프가 표시됨. 해당 대용량 파일은 표시하지 않는 큰 이미지를 포함한 합성 파일임. ARM64 및 실기기 시험은 아님.
- 합성 PPTX의 두 번째 슬라이드 표시 중 `dumpsys meminfo` 단일 시점 측정에서 앱 프로세스 PSS 81,648KiB, 연결된 WebView 렌더러 PSS 97,431KiB를 확인함. 두 프로세스 합계는 179,079KiB임. 순차 측정된 순간값으로 최대치·실기기 수치·변경 전후 비교가 아님.
- F-Droid의 LibreOffice Viewer 26.2.6.3 ARM64 APK는 87,682,841바이트, SHA-256은 `751ac3836890b79a56801bf6d9a2788cda3761ab5131a4f0b6abfbad822bb475`임. APK 내 ARM64 네이티브 라이브러리는 압축 합계 73,764,438바이트, 압축 해제 합계 204,803,000바이트임. 그중 `liblo-native-code.so`는 각각 70,927,376바이트와 196,227,296바이트임.
- 위 ARM64 APK를 Android 15 x86_64 에뮬레이터에 설치함. 에뮬레이터는 ARM64 바이너리 변환을 지원하고 설치된 앱의 `primaryCpuAbi`가 `arm64-v8a`로 확인됨. 공개 PPTX 두 번째 슬라이드의 그래프와 왼쪽 제목, 공개 DOCX 첫 페이지의 제목·본문·표, 공개 XLSX 첫 시트 일부의 제목·표를 확인함. 전체 서식과 값의 일치는 미검증 상태임. 별도 앱 및 변환 실행 결과로, MIN VIEWER 직접 통합이나 ARM64 실기기 시험은 아님.
- 별도 ARM64 LibreOffice Viewer도 약 25.36MB 합성 PPTX를 열고 두 번째 슬라이드를 표시함. 표시 중 프로세스 PSS는 한 시점에 545,424KiB였음. ARM64 바이너리 변환과 이전 문서 실행 이력이 포함된 순간값으로, 최대치·실기기 성능 및 위 MIN VIEWER 수치와의 공정한 비교는 아님.
- 별도 실험용 앱에서 같은 F-Droid ARM64 네이티브 라이브러리, 자산과 동일 버전 공식 JNI 바인딩을 직접 초기화함. 공개 PPTX·DOCX·XLSX를 앱 전용 임시 파일로 복사해 각 형식을 인식하고 타일을 그림. PPTX 두 번째 슬라이드의 그래프·왼쪽 제목과 DOCX 제목·본문·표를 확인함. XLSX는 초기 표시 영역을 제한해 가독성을 확보했으나 오른쪽이 잘리고 스크롤이 없어 전체 내용을 확인할 수 없음. 이 앱은 MIN VIEWER 본 앱이 아니며 기능·예외 처리와 배포 라이선스 검토가 완료되지 않음.
- 위 직접 연동 시험 APK는 네이티브 라이브러리를 압축하지 않은 경우 212,783,531바이트, 압축해 패키징한 경우 87,971,987바이트임. 압축 패키징한 앱에서도 ARM64 변환 에뮬레이터의 동일 초기화·렌더링 시험이 성공함. 압축 APK 크기는 설치 후 용량이나 실행 메모리와 다름.
- 압축 패키징한 직접 연동 시험 앱의 공개 PPTX 표시 중 단일 시점 PSS는 395,966KiB임. ARM64 변환 에뮬레이터 결과로 최대 메모리, 실기기 메모리 또는 다른 앱과의 공정한 비교가 아님.
- MIN VIEWER에 직접 빌드한 ARM64 엔진과 JNI 바인딩을 포함하고 DOCX·XLSX·PPTX 선택 시 LibreOffice 시험 화면을 먼저 엶. 돌아온 뒤 `경량 엔진 보기` 또는 `LibreOffice 시험`을 사용자가 선택할 수 있음. 별도 프로세스와 단일 작업 스레드에서 문서를 열고 타일을 표시함. 공개 DOCX 첫 페이지, PPTX 슬라이드 전환, XLSX 초기 영역·가로 드래그 및 두 시트 합성 XLSX의 시트 전환을 시험함. 완성된 Office 뷰어 또는 전 형식의 최종 엔진 채택을 뜻하지 않음.
- Office 선택 시 기존 WebView 엔진의 파일 읽기를 피하며, 시험 경로에 재진입할 때 기존 문서를 해제함. 복귀 후 경량 엔진을 선택한 경우에만 문서를 다시 엶. 앱 전용 입력 임시 파일은 정상 종료·오류 시 삭제하고 강제 종료 시 남은 입력 파일은 다음 시험 시작 시 정리함. 엔진 내부 캐시는 전용 디렉터리에 두며 엔진 프로세스의 다음 초기화 시 정리함. 시험 화면을 완전히 닫으면 문서 정리 후 별도 엔진 프로세스를 종료함.
- 같은 약 25.36MB 합성 PPTX를 여는 한 시점에서 해제 전 앱·WebView·Office PSS는 각각 97,787·119,238·387,829KiB였고, 해제 후 별도 실행의 측정값은 96,145·66,971·384,490KiB였음. 이후 LibreOffice를 바로 여는 방식의 별도 실행에서는 98,578·57,791·390,385KiB로 관찰됨. 순차 측정된 단일 표본과 ARM64 변환 에뮬레이터 결과이므로 최대치나 재현 가능한 성능 향상으로 단정할 수 없음.
- LibreOffice 시험은 암호화된 OOXML 입력을 아직 지원하지 않으며, 시트는 드래그 이동만 제공함. 확대·축소, 페이지 목록, 검색, 모든 페이지·시트 및 사용자 글꼴·실기기·실사용 문서 검증은 남아 있음. 과거 실험 과정에서 기존 공용 캐시에 생성된 `lu*.tmp` 디렉터리는 새 전용 캐시로 이관하거나 정리하지 않았음.
- 위 LibreOffice Viewer는 별도 앱이며 기능과 엔진 구성이 다름. MIN VIEWER 통합 APK, 설치 크기, 최대 메모리 또는 동일 조건의 속도 비교로 해석할 수 없음.

### 회귀 시험 재실행

- `node --test tests/*.test.mjs`: WebView 문서 선택·교체·오류·자원 정리 및 공개 PPTX 이미지 시험임. PPTX 이미지 시험은 `.research`의 공개 표본이 없으면 건너뜀.
- `node tests/lok-integration.mjs pptx`: 공개 PPTX 열기·슬라이드 전환·화면 크기 변경·기존 뷰어 복귀·별도 프로세스 종료를 시험함.
- `node tests/lok-integration.mjs docx`, `xlsx`, `sheets`, `large`, `invalid`: 공개 DOCX·XLSX, 두 시트 합성 XLSX, 약 25.36MB 합성 PPTX 및 형식 불일치 시험임. XLSX 화면 차이 검사는 `.research/py`의 Pillow를 사용함.
- 위 통합 시험은 Windows의 `.research/sdk/platform-tools/adb.exe`, 디버그 APK, 320×640 에뮬레이터 및 `/sdcard/Download`에 준비된 해당 시험 파일을 필요로 함. 에뮬레이터만 허용하며 시험 중 창 크기와 앱 실행 상태를 변경함.

## PDF 보기와 Office 화면 추가 시험

- Android 기본 `PdfRenderer`를 사용하는 PDF 시험 화면을 추가함. 연속 스크롤, 한쪽 보기, 표지 단독 두쪽 보기, 페이지 이동 및 페이지 미리보기 목록을 제공함. 선택한 보기와 페이지는 화면 재생성 시 복원하도록 구현함.
- 35쪽 공개 HWP에 함께 제공된 PDF를 Android 15 x86_64 에뮬레이터의 320×640 화면에서 열어 위 보기 전환과 미리보기 선택을 시험함. 3쪽 선택 후 창 크기를 640×320으로 변경했을 때 페이지 번호가 유지됨. PDF 확대·축소, 검색, 암호 문서, 실제 기기 및 다양한 PDF는 미검증 또는 미구현 상태임.
- PDF 페이지와 미리보기의 비트맵 캐시는 각각 16MiB와 4MiB로 제한함. 파일 제공자가 직접 탐색 가능한 파일을 제공하지 않으면 앱 전용 임시 파일로 스트리밍 복사함. 캐시 제한은 전체 프로세스 메모리 상한을 의미하지 않음.
- 한글 문서에서 검색어의 첫 결과가 있는 페이지로 이동하는 시험 기능을 추가함. 공개 HWP 1개에서 `2020` 검색 시 6쪽으로 이동함. 검색어 강조·다음 결과 이동, HWPX 및 표 셀 검색 결과의 정확도는 미검증 상태임. 검색은 WebView 실행 경로에서 수행하므로 대용량 문서의 반응성 확인이 필요함.
- LibreOffice 화면에 버튼과 손가락 동작을 이용한 확대·축소를 추가함. 공개 PPTX에서 확대·축소 버튼, 존재하는 문자열 검색과 없는 문자열 안내를 에뮬레이터에서 시험함. 현재는 표시된 비트맵을 확대하므로 고배율에서 선명도가 제한됨. 검색 위치 표시와 다른 형식·복잡한 문서의 정확도, 손가락 동작은 추가 확인이 필요함. Office 썸네일은 미구현 상태임.
- LibreOffice 타일 렌더링의 직접 메모리 버퍼를 페이지 간 재사용하고 문서 종료 시 참조를 해제함. 반복 할당을 줄이는 변경이며 최대 메모리 감소 효과는 측정하지 않음. 엔진 내부 메모리 및 한글 엔진의 전체 파일 로딩 문제는 남아 있음.
- 약 25.36MB 합성 PPTX의 첫 화면에서 Office 별도 프로세스의 PSS는 단일 시점에 391,230KiB였음. 변경 전 별도 실행의 390,385KiB와 비슷한 수준이나, 최대값과 동시 측정된 전체 앱 메모리가 아니므로 변경 효과로 해석할 수 없음. 사용자 실문서 및 ARM64 실기기는 미검증 상태임.
- 추가 디버그 APK는 ARM64 엔진 포함 106,077,115바이트임. 설치 후 크기, 릴리스 크기 및 다른 앱과 동일 조건의 비교 결과는 아님. 최종 병합 APK의 선언 권한은 `aapt dump permissions` 기준 없음.
- PDF 미리보기의 첫 항목은 화면에서 확인되었으나 자동화 접근성 트리에 일관되게 나타나지 않아 접근성 확인이 필요함. 실기기, 폴더블·분할 화면 및 대용량 문서의 최대 메모리는 미검증 상태임.

## CSV와 외부 앱 전달 시험

- CSV를 기기 내에서 읽고 표로 표시하는 시험 화면을 추가함. 쉼표 구분, 따옴표 이스케이프와 따옴표 안의 쉼표·줄바꿈을 처리함. UTF-8과 CP949의 자동 판별을 시도하며 사용자가 인코딩을 변경할 수 있음. UTF-8 BOM을 처리함.
- 한 번에 최대 100행씩 읽어 표시함. 이후 페이지는 파일 처음부터 다시 읽어 찾으므로 매우 큰 파일의 뒷부분 이동 속도는 미검증 상태임. 한 행은 최대 131,072자, 열은 최대 512개로 제한하며 초과 시 오류를 표시함. 쉼표 이외의 구분자는 현재 미지원임.
- Android의 파일 열기와 단일 파일 공유를 수신하도록 등록함. 전달받은 `content://` URI의 읽기 권한을 사용하며 문서 화면에도 권한을 전달함. 권한이 없거나 지원하지 않는 입력은 오류를 표시함. MIME 형식이 일반 텍스트 또는 이진 파일로 지정되는 경우도 지원하기 위해 연결 프로그램에 관련 없는 파일이 표시될 수 있음.
- HWPX의 `application/hwp+zip` 및 `application/octet-stream` 전달도 허용함. 한컴은 HWPX MIME 형식의 공식 등록 여부와 두 값의 사용 가능성을 [개발자 포럼](https://forum.developer.hancom.com/t/hwpx-http-content-type-application-hwp-zip/1752)에서 설명함.
- Android 15 에뮬레이터에서 별도 시험 앱이 임시 권한과 함께 제공한 CSV를 열기·공유로 표시하고, 권한을 부여하지 않은 경우 오류가 나타남을 확인함. 같은 시험 앱의 PDF·HWP·HWPX·PPTX 열기도 확인함. 카카오톡·이메일 앱 자체와 사용자 실기기에서의 전달은 시험하지 않음.
- CSV 표본의 UTF-8 BOM, 쉼표와 줄바꿈이 포함된 인용 필드, CP949 한글, 201행 페이지 전환 및 닫히지 않은 따옴표 오류를 에뮬레이터에서 시험함. 다양한 인코딩·구분자·초대용량 파일과 사용자 실문서는 미검증 상태임.
- 이 변경을 포함한 ARM64 디버그 APK는 106,096,691바이트이며, `aapt dump permissions` 기준 선언된 권한은 없음. 설치 크기 및 실기기 성능은 미측정 상태임.

## 보기 기능·메모리 추가 시험

- LibreOffice의 세로로 긴 페이지가 일부만 그려지는 문제를 합성 DOCX로 재현함. 페이지 전체를 제한된 크기로 렌더링하고 스크롤하도록 변경한 뒤 문서 아래쪽 표시를 화면에서 확인함. 공개 계약서 DOCX 첫 페이지의 제목·본문·표와 공개 PPTX 두 번째 슬라이드의 그래프·제목을 함께 제공된 기준 PDF와 육안 비교함. 전체 문서 및 글꼴·세부 줄바꿈의 일치는 미검증 상태임.
- Office 확대 시 기존 비트맵 확대 대신 확대된 영역을 다시 렌더링하고 이동하도록 변경함. 한 번의 렌더링 크기는 최대 960×1600픽셀로 제한함. 확대·이동과 화면 크기 변경 후 확대 비율 복원을 에뮬레이터에서 시험함. 다양한 비율과 실제 기기의 핀치 조작은 미검증 상태임.
- PowerPoint의 썸네일을 필요한 항목부터 생성하고 4MiB 캐시를 사용함. 좁은 창에서는 목록 창을, 840dp 이상에서는 숨길 수 있는 나란한 목록을 제공함. 목록에서 슬라이드 선택과 확대된 화면 이동을 공개 PPTX로 시험함.
- 한글 원본 페이지의 연속·한쪽·두쪽 보기를 추가함. 두쪽 보기는 표지를 오른쪽에 단독 배치하고 이후 두 페이지씩 표시함. 화면 주변 페이지만 SVG로 생성하고 멀어진 페이지의 표시 자원을 정리함. 공개 HWP에서 연속 스크롤, 표지, 두쪽 이동, 화면 크기 변경 및 본문·표 셀 검색 결과 이동을 시험함. 검색 결과가 5,000개를 넘으면 추가 결과 이동을 제공하지 않음. HWP/HWPX 입력 전체를 읽는 엔진 구조와 검색 시 반응성 검증은 남아 있음.
- PDF 확대·축소, 내장 텍스트 검색과 다음 결과 이동·강조 표시를 추가함. 현재 검색은 Android 15(API 35) 이상에서만 제공하며 이미지로만 된 문서의 OCR은 제공하지 않음. 기본 검색 API의 조건은 [Android 공식 문서](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer.Page)를 참고함. Android 10~14 대안으로 [PdfBox-Android](https://github.com/TomRoush/PdfBox-Android)의 텍스트 추출을 검토했으나, 좌표·문서 호환성·메모리·APK 증가량 검증 전이므로 포함하지 않음.
- PDF도 840dp 이상에서 페이지 목록과 문서를 나란히 표시하며 목록을 숨길 수 있음. 320×640, 640×320, 1280×800 및 1100×700으로 크기를 조정한 Android 15 x86_64 에뮬레이터에서 페이지·확대 비율·넓은 목록의 복원을 시험함. PDF 확대는 제한된 해상도의 페이지 비트맵을 사용하므로 고배율과 고해상도 태블릿의 선명도는 추가 검증이 필요함.
- 별도 시험 앱이 탐색할 수 없는 파이프 스트림으로 전달한 공개 PDF를 열고, 닫은 뒤 생성된 임시 PDF가 정리됨을 확인함. 강제 종료로 남은 임시 PDF는 다음 PDF 실행 시 정리하도록 수정하고 에뮬레이터에서 확인함. 손상된 PDF와 형식이 맞지 않는 Office 파일의 오류 안내도 확인함. 카카오톡·이메일 앱 자체의 파일 제공 방식은 별도 검증이 필요함.
- Office·PDF·CSV를 열 때 사용하지 않는 WebView를 지연 생성하거나 해제하도록 변경함. 약 25.36MB 합성 PPTX의 동일 화면을 ARM64 변환 에뮬레이터에서 연 순차 단일 시점 측정값은 변경 전 앱 95,531KiB·WebView 58,468KiB·Office 392,676KiB, 변경 후 앱 43,295KiB·Office 388,611KiB였음. 각각의 합계는 546,675KiB와 431,906KiB임. 측정 시점과 프로세스 조건의 차이가 있으므로 최대 메모리나 실기기 개선량을 의미하지 않음.
- 최종 빌드에서 같은 합성 PPTX를 강제 종료 후 다시 열었을 때 앱 PSS 44,014KiB, Office PSS 391,988KiB였음. 4배 확대 뒤 Office PSS는 402,344KiB로 관찰됨. 시작부터 문서 화면 감지까지 5,414ms가 걸렸으며 ADB 실행·화면 검사 지연이 포함된 단일 관찰값임. 해당 파일은 표시하지 않는 큰 이미지를 포함하므로 고해상도 이미지 렌더링 성능이나 실기기 첫 화면 시간을 대표하지 않음. 재측정 도구는 `tests/office-benchmark.mjs`임.
- 위 보기 기능을 포함한 ARM64 디버그 APK는 106,141,643바이트이며, `aapt dump permissions` 기준 선언된 권한은 없음. 배포용 APK 크기와 설치 후 크기는 미측정 상태임.
- PDF 미리보기 첫 항목의 접근성 트리 문제, 실제 다중 창·폴더블 및 기기별 핀치·성능, 암호 문서, 사용자 글꼴, Word·한글 모바일 재배치 보기와 대표 실문서의 전체 내용 검증은 남아 있음. 카카오톡·이메일 앱에서의 직접 전달도 실기기 미검증 상태임.

## 뷰어 화면과 최근 위치 시험

- PDF·한글·Office에 공통 남색 상단·하단 도구를 적용함. 좁은 화면의 PDF 문서 영역과 넓은 화면의 PowerPoint 슬라이드 목록·문서 배치를 에뮬레이터에서 확인함.
- PDF 두쪽 문서에서 한쪽 보기, 2쪽, 확대 150%를 선택한 뒤 최근 문서에서 해당 상태가 복원됨을 자동 검사함. PDF 검색 결과를 확인함. 한글 시험 문서에서 두쪽 보기와 2쪽 복원 후 다음 조작 시 4쪽 이동을 확인함. PowerPoint 시험 문서에서 2번 슬라이드 복원을 확인함.
- 1280×800 x86_64 에뮬레이터의 PowerPoint 표본 표시 중 단일 시점 Office 프로세스 PSS는 394,912KiB였음. 다른 실행 이력과 ARM 바이너리 변환이 포함된 순간값이며 최대치·실기기 수치 또는 성능 개선 비교가 아님.
- 해당 시험 당시 PDF·한글·Office의 모든 기능과 형식, 실제 다중 창·실기기, 강제 종료 후 복원은 미검증 상태였음. 한글 확대 상태 저장도 미구현 상태였음. 기존 일부 UI 통합 시험은 이전 버튼 배치에 의존하므로 새 조작부에 맞춘 갱신이 필요함.

## 강제 종료 복원과 메모리 재측정

- PDF의 읽기 위치·보기 방식·확대 상태를 읽는 동안 저장함. Office는 별도 프로세스에서 앱 내부 전용 provider로 위치·확대 상태를 전달함. 한글은 WebView 배율 변화와 페이지·보기 방식을 저장하고 재개 시 배율을 복원함.
- 에뮬레이터에서 강제 종료 후 PDF의 페이지·보기 방식·확대, HWP의 페이지·확대와 복원 뒤 축소, PowerPoint의 슬라이드·확대 복원을 확인함. HWP 확대 시험은 160dpi 및 280dpi 에뮬레이터에서 수행함. 손가락 핀치와 실기기는 미검증 상태임.
- 25,360,052바이트 합성 PPTX의 최초 화면에서 측정한 변경 전 Office PSS는 389,203KiB임. 화면 너비에 맞춰 렌더 크기를 줄이는 실험에서는 389,895KiB였음. 두 수치는 순차 단일 시점이며 통계적 비교나 최대치가 아님. 뚜렷한 개선이 확인되지 않아 렌더 크기 변경은 적용하지 않음.
- 강제 종료 직전의 저장 처리나 일시 권한만 받은 문서는 복원을 보장할 수 없음. 카카오톡·이메일의 실제 파일 전달과 권한 만료 후 재선택은 실기기 확인이 필요함.

## Office 메모리와 읽기 전용 엔진 비교

- Android 15 x86_64 에뮬레이터에서 ARM64 LibreOfficeKit 26.2.6.3을 바이너리 변환으로 실행함. 소형 PowerPoint·25,360,052바이트 합성 PowerPoint·Word·Excel 각각의 Office 프로세스 PSS는 단일 시점에 388,195·388,709·399,670·391,006KiB였음. 합성 파일은 화면에 표시하지 않는 큰 이미지를 포함하므로 이미지가 많은 실문서를 대표하지 않음.
- 합성 PowerPoint 시험에서 단계별 Office 프로세스 PSS는 자산 준비 후 33,784KiB, 엔진 시작 후 208,877KiB, 문서 로드 후 367,872KiB, 첫 화면 렌더 후 389,725KiB였음. 측정 호출이 포함된 순차 순간값으로 단계별 최고치나 실기기 수치를 의미하지 않음. 별도 분류에서 `.so mmap`과 `Other mmap` 비중이 컸으나 후자의 전체 원인은 확인하지 못함.
- 시작 단계별 경과 시간의 별도 단일 관찰에서 25MB 입력 복사는 약 63ms, 엔진 초기화 약 719ms, 문서 로딩 약 888ms, 첫 렌더링 약 109ms였음. 에뮬레이터와 화면 검사 지연이 포함된 전체 열기 시간과 구분이 필요함.
- PowerPoint 미리보기마다 새로 만들던 임시 직접 버퍼를 문서 렌더링과 공유하도록 변경함. 두 작업은 기존 단일 Office 작업 스레드에서 순서대로 수행됨. 150장 합성 문서에서 전후 각각 두 번 스크롤한 뒤의 PSS는 변경 전 475,007·469,220KiB, 변경 후 475,448·472,965KiB였음. 측정 시점이 다른 소수 표본으로 전체 PSS 감소는 입증되지 않음. 같은 초기 화면의 변경 전후 문서·미리보기 영역은 픽셀 단위로 동일했음.
- 슬라이드 표본 생성·검사 준비: `npm.cmd install --prefix .research/office-stress --ignore-scripts --no-audit --no-fund pptxgenjs@4.0.1`, `node tests/office-thumbnail-fixture.cjs`. 생성된 `.research/office-stress/thumbnail-stress.pptx`를 에뮬레이터의 `/sdcard/Download/min-thumbnail-stress.pptx`로 복사하고 미디어 스캔 후 `node tests/office-thumbnail-integration.mjs`를 실행함. 화면 차이 검사는 `.research/py`의 Pillow가 필요함.
- 별도 시험 앱에서 읽기 전용 `@silurus/ooxml@0.80.2`를 로컬 WebView로 실행함. 라이브러리는 MIT 라이선스이며 Rust/WASM 파서와 Canvas 표시 방식을 사용함. 해당 앱은 실제 MIN VIEWER와 기능 구성이 다르며 HWP·PDF 및 기존 앱 기능을 포함하지 않음. 별도 시험 APK는 5,405,276바이트였고 이를 완성 앱의 크기로 간주할 수 없음. [라이브러리 공식 저장소](https://github.com/yukiyokotani/office-open-xml-viewer), [Android 연결 사례](https://github.com/Faur4n/androidFileViewer/blob/master/viewer/README.md)
- 320×640 에뮬레이터, 소형 PowerPoint의 두 번 시험에서 LibreOffice 앱·Office 프로세스 PSS 합계는 441,285·440,406KiB, 대안의 앱·WebView 렌더러 합계는 169,029·166,521KiB였음. UI 감지 시간은 각각 약 5.16·5.17초와 2.72·3.27초였음. 두 프로세스의 측정은 순차 순간값이며 표시 감지 지연과 다른 UI 구성이 포함됨. LibreOffice는 ARM64 변환 실행이므로 실기기 비교로 해석할 수 없음.
- 대안은 시험 PowerPoint의 차트와 Excel의 표를 표시했음. Word 계약서 표본은 원본 비율로 보정한 뒤에도 제공된 기준 PDF 및 LibreOffice 표시와 표 위치·본문 배치 차이가 관찰됨. 전체 내용의 누락 여부와 대표 문서 호환성은 미검증 상태이므로 기존 엔진을 대체하지 않음.

## Excel 시트 목록

- LibreOffice 엔진에서 시트 이름을 읽어 시트 목록과 직접 이동을 제공함. 선택을 취소하면 현재 시트를 유지함.
- Android 15 x86_64 에뮬레이터에서 ARM64 변환 실행으로 시트 2개가 포함된 시험 XLSX의 이름 표시, 선택 취소 및 양방향 이동을 확인함. 실기기, 많은 시트·숨김 시트·암호 문서 및 시트 위치의 강제 종료 후 복원은 미검증 상태임.

## Word 페이지 목록

- LibreOffice 엔진이 페이지 위치를 반환하는 Word 문서에서 페이지 번호 목록과 직접 이동을 제공함. 목록을 닫으면 현재 위치를 유지하며 미리보기 이미지를 생성하지 않음.
- Android 15 x86_64 에뮬레이터의 ARM64 변환 실행으로 페이지 나누기 2개를 포함한 3쪽 합성 DOCX에서 목록 표시, 선택 취소 및 1쪽과 3쪽 사이 이동을 확인함. 실기기, 실제 복잡 문서 및 긴 문서의 페이지 목록과 위치 복원은 미검증 상태임.

## 파일 열기와 최근 문서 안정화

- 시스템 파일 선택기로 지속 읽기 권한을 받은 CSV는 문서를 성공적으로 읽은 뒤 최근 목록에 등록하고 100행 단위 위치와 선택한 인코딩을 저장함. 임시 권한만 받은 파일은 기존 정책에 따라 최근 목록에 추가하지 않음.
- 201행 합성 CSV를 파일 선택기로 열고 CP949와 두 번째 구간을 선택한 뒤 앱 강제 종료 및 최근 목록 재진입 시 해당 위치와 인코딩 복원을 확인함. 시험 파일의 이름을 변경해 기존 항목으로 열 수 없는 경우 재선택 안내를 확인함.
- 외부 전달 시험 앱에서 CSV의 열기·공유·ClipData 전달 및 권한 없는 입력 오류를 확인함. PDF·HWP·HWPX·PPTX의 외부 열기 경로를 에뮬레이터에서 시험함. 실제 카카오톡·이메일 앱과 실기기는 미검증 상태임.
- PDF 텍스트 검색은 Android 15(API 35) 이상에서 제공함. Android 10~14용 별도 검색 엔진은 현재 구현 범위에서 제외함. 이미지 전용 PDF의 OCR은 제공하지 않음.

## Word·Excel 최근 위치 복원

- Office 문서에서 기존 페이지·시트·슬라이드 및 확대율 외에 현재 표시 영역의 좌표를 최근 문서에 저장함. 좌표가 없는 기존 기록은 기본 위치로 열도록 유지함. 문서 원본 변경 없이 앱 내부에 저장함.
- 3쪽 합성 DOCX와 두 시트 합성 XLSX를 Android 15 x86_64 에뮬레이터의 ARM64 변환 실행 환경에서 시스템 파일 선택기로 열고, 마지막 페이지 또는 시트에서 150% 확대 및 화면 이동 후 일반 종료와 강제 종료를 시험함. 같은 320×640 창에서 다시 연 화면의 문서 영역을 픽셀 비교해 일치함을 확인함. 선택 직후 종료, 다른 창 크기 및 다양한 실문서는 미검증 상태임.
- 시험용 외부 앱이 DOCX와 XLSX를 각각 `ACTION_VIEW`와 `ACTION_SEND`로 전달할 때 문서가 열림을 확인함. 각 확장자의 손상 입력 및 읽기 권한을 부여하지 않은 입력에 오류가 표시됨을 확인함. 실제 카카오톡·이메일, 임시 권한 만료, 실기기 및 실제 사용자 문서는 별도 검증이 필요함.

## 문서 표시 품질 비교 및 수식 경고

## 슬라이드 목록과 검색 탐색

- PowerPoint는 840dp 이상 창에서 왼쪽 미리보기 목록을 한 열로 표시하고 목록 버튼으로 애니메이션을 적용해 접고 펼침. 좁은 창에서는 기존 별도 목록 창을 유지함. 목록 생성은 필요한 항목 중심으로 수행하고 기존 4MiB 썸네일 캐시를 유지함.
- Office에 다음 검색 결과 이동을 추가하고 검색 결과 위치를 기존 페이지·시트·슬라이드 표시와 강조 영역으로 나타냄. Excel 검색은 현재 시트에 한정하며 시트를 바꾼 뒤 다음 결과 기능으로 해당 시트에서 검색함. 첫 셀만 일치하는 사례에서는 일반 검색 실패 시 전체 검색 경로로 재확인함. 결과가 없을 때 엔진의 실패 응답만으로 오류 여부를 구분할 수 없는 경우 결과 없음 또는 검색 실패로 안내함.
- 한글 페이지 목록 선택 시 원래 페이지로 되돌아갈 수 있는 문제를 수정하고 현재 검색 결과의 순번을 표시함. 검색된 본문 또는 표 셀의 좌표를 확인할 수 있으면 해당 글자를 강조하고 화면 위치를 이동함. 좌표를 얻지 못하면 페이지 이동은 유지하고 강조 불가를 안내함.
- Android 15 x86_64 에뮬레이터에서 1280×800 및 320×640 창의 목록 배치와 선택, 150장 합성 PowerPoint의 목록 개폐 후 화면 유지를 확인함. 3쪽 합성 Word·PowerPoint의 연속 검색과 결과 없음, 두 시트 합성 Excel의 시트 내 검색·첫 셀 검색·시트 변경 후 검색 및 결과 없음을 시험함. 공개 HWP에서 목록의 3쪽 선택 및 검색 결과 1/3에서 2/3 이동을 확인함.
- 검색 결과가 많은 Excel 파일에서 전체 검색 재확인의 최대 메모리·반응성, 여러 형식의 복잡한 문서·검색 범위, 실제 기기에서 애니메이션의 부드러움 및 폴더블·분할 화면은 추가 검증이 필요함. PDF 검색은 기존 Android 15 이상 동작을 유지함.

## 한글 검색 결과 강조

- rhwp의 본문 및 표 셀 선택 사각형을 사용해 표시 중인 검색 결과에 반투명 강조를 적용함. 다음 결과 이동 시 이전 강조를 교체하며 결과가 없으면 강조를 제거함. 해당 결과 위치로 화면을 이동함.
- Android 15 x86_64 에뮬레이터에서 공개 HWP의 본문 `2020`과 표 셀 `2021`, 다음 결과 이동, 연속 및 한쪽 보기의 강조를 확인함. 공개 HWPX의 `3` 검색 결과는 연속 및 두쪽 보기에서 확인하고 결과 없음 시 강조 제거를 시험함. 좌표 조회 실패 시 페이지는 반환하고 강조 불가를 안내하는 단위 검사를 수행함.
- 각주·머리말·중첩 표, 줄을 넘는 검색어 및 다양한 실문서의 좌표 정확도, 고배율·화면 크기 변경·실기기 동작과 대용량 문서의 검색 반응은 미검증 상태임. 검색 결과 위치를 모두 감지한다고 보장하지 않음.

## Excel 시트 간 검색 시험

- Excel 검색 시 현재 시트의 첫 결과부터 탐색하고, 다음 결과가 현재 시트의 앞부분으로 순환하면 다음 시트를 검색하도록 변경함. 마지막 시트 이후에는 첫 시트로 순환함.
- Android 15 x86_64 에뮬레이터의 합성 XLSX에서 첫 시트의 두 결과, 결과가 없는 중간 시트 건너뛰기, 세 번째 시트 결과 표시 및 전체 시트에 결과가 없는 경우의 안내를 시험함.
- 숨김 시트, 병합 셀, 같은 셀의 여러 결과, 대용량 파일의 전체 검색 비용과 실기기 동작은 미검증 상태임. 첫 결과 검색에 LibreOffice의 전체 결과 검색을 사용하므로 결과가 많은 문서에서 메모리와 응답 시간 측정이 필요함.

## 암호 문서·CSV·화면 테마 시험

- Android 15 이상의 내장 PDF 렌더러에 비밀번호 입력을 연결함. AES-256 합성 PDF에서 틀린 비밀번호 안내와 올바른 비밀번호 입력 후 표시를 Android 15 에뮬레이터에서 확인함. 이전 버전은 암호 PDF를 열 수 없다는 안내를 제공함. 다른 암호 방식 및 Android 10~14 실기기 안내는 미검증 상태임.
- LibreOfficeKit의 암호 콜백을 연결함. Microsoft Office에서 암호를 설정한 합성 DOCX·XLSX·PPTX 각각에 대해 잘못된 비밀번호 재입력과 올바른 비밀번호로 열기를 에뮬레이터에서 확인함. 다양한 Office 암호 방식 및 실기기는 미검증 상태임. 비밀번호를 설정 또는 최근 문서 목록에 저장하지 않음.
- rhwp 0.9.0의 암호 열기 API를 연결함. 해당 엔진으로 만든 암호 HWP와 HWPX에서 비밀번호 오류 안내 및 올바른 비밀번호 입력 후 열기를 Android 15 에뮬레이터에서 확인함. 엔진은 HWP5 EncryptVersion 4, 압축 HWP3와 ODF AES-256-CBC HWPX를 지원한다고 문서화하며 구형·비압축 HWP3 암호와 DRM은 지원하지 않음. 한컴오피스에서 만든 다양한 암호 문서와 실기기는 미검증 상태임.
- CSV에 행 번호 이동과 범위를 벗어나는 번호의 오류 안내를 추가함. 한 번 열린 입력 스트림을 다음 100행 탐색에 재사용하도록 변경하고, 재열기를 허용하지 않는 시험 제공자의 201행 CSV에서 연속 페이지 이동을 확인함. 인코딩 변경·이전 페이지·임의 행 이동 시에는 스트림을 다시 엶.
- Android 15 x86_64 에뮬레이터와 500,001행·10,777,811바이트 합성 CSV의 단일 전후 시험에서 499,800행 이동 후 다음 100행 화면 확인 시간은 각각 7,481ms와 2,091ms였음. 초기 행 이동은 각각 7,518ms와 8,036ms였으며 여전히 처음부터 읽음. ADB 및 화면 감지 시간이 포함된 단일 관찰이므로 실기기 속도나 일반적인 성능 향상으로 단정할 수 없음.
- 시작 화면에서 시스템·라이트·다크 테마를 선택할 수 있도록 함. 다크 테마 선택 후 앱 재시작 시 유지와 시스템 다크 모드 반영을 에뮬레이터에서 확인함. PDF·한글·Office 문서 원본 색상은 변경하지 않으며 모든 화면과 실기기의 색상·접근성 검증은 남아 있음.
- 한글의 모바일 텍스트 전용 보기를 추가함. 페이지별 추출 텍스트만 재배치하며 표·그림·수식 및 이미지로 된 본문 등이 누락될 수 있음을 안내함. 공개 HWP의 3쪽에서 본문 텍스트와 원본 보기 복귀를 확인하고, 강제 종료 후 텍스트 보기와 3쪽 복원을 시험함. 완전한 한글 모바일 재배치가 아니며 텍스트 추출이 불가능한 페이지도 있음.
- Word 원본 보기에서 모바일 보기로 전환하고 다시 원본으로 돌아가는 경로를 추가함. 경량 엔진의 공개 계약서 DOCX에서 좁은 화면의 본문 재배치를 확인함. 3쪽 합성 DOCX에서 시험용 창 크기 변경 시 모바일 보기 유지 및 강제 종료 후 모바일 보기와 원본 2쪽 복원을 확인함. 이미지·표 등 내용과 배치 누락 가능성을 전환 전과 화면에서 안내함. 암호 Word의 모바일 보기와 강제 종료 후 원본 확대·이동 위치 복원은 미검증 상태임.
- 사용자 TTF·OTF 글꼴을 시스템 선택기로 추가해 앱 전용 저장소에 보관하고, 글꼴 이름 목록과 삭제를 제공함. 사용 권한을 보유한 글꼴만 사용하도록 안내함. 에뮬레이터에서 시험 글꼴 추가 전후의 HWPX와 DOCX 화면 변화를 확인했으며, 앱 내 복사본 삭제와 원본 파일 유지를 확인함. LibreOffice에는 앱 내부 심볼릭 링크로 글꼴을 전달함. 글꼴의 모든 문자·굵기·폰트 컬렉션, PDF 적용 및 Excel·PowerPoint 실문서는 미검증 상태임.
- 15쪽 합성 Word 문서를 Microsoft Word의 PDF 출력과 Android 15 에뮬레이터에서 비교함. 양쪽 모두 15쪽으로 열렸으며, 8쪽의 제목·본문·9개 셀·그림과 15쪽의 제목·본문을 육안으로 확인함. 단순한 합성 표본의 일부 페이지만 확인한 결과이며 실제 장문 문서 전체의 서식 일치를 의미하지 않음. 비교 자료는 로컬 `.research/quality`에 보관함.
- 사각형·원·그림·한글 문자가 포함된 3장 합성 PowerPoint를 Microsoft PowerPoint의 PDF 출력과 비교함. 앱의 두 번째 슬라이드에서 해당 요소가 보였으며 원본에서 도형이 본문을 가리는 배치도 동일하게 관찰됨. 한 표본의 육안 비교로, 다양한 글꼴·애니메이션·복잡 도형의 호환성은 미검증 상태임.
- Android 15 에뮬레이터에서 비행기 모드를 켠 뒤 로컬 HWP·DOCX·PDF 각 1개를 열었으며 시험 후 기존 네트워크 설정을 복원함. 실기기와 다른 형식·외부 앱에서 전달한 문서의 오프라인 동작은 별도 확인이 필요함.

## 파일 안정성 추가 확인

- Word 암호 입력을 취소한 뒤 빈 뷰어가 남던 문제를 수정함. 일반 열기와 최근 문서 열기에서 취소 시 시작 화면으로 돌아가며, 사용자 취소를 접근 오류로 안내하지 않도록 함.
- Android 15 에뮬레이터에서 손상된 PDF·HWP·HWPX·Word·Excel과 외부 한글·Office 문서의 권한 거부 안내를 확인함. PDF·HWP·HWPX·Word·Excel·PowerPoint의 시험용 암호 문서에서 잘못된 비밀번호와 올바른 비밀번호 입력을 확인함. 암호 방식 전체와 실제 기기 호환성은 미검증 상태임.
- 시스템 선택기로 연 PDF·HWP·Word 시험 파일의 원본을 삭제한 뒤 최근 문서에서 열어 재선택 안내를 확인함. 실제 URI 권한 만료를 재현한 결과와는 구분함.
- PDF·HWP·Word 시험 파일을 시스템 선택기로 연 뒤 파일은 보존하고 해당 URI의 지속 읽기 권한만 해제함. 최근 문서로 다시 열 때 세 형식 모두 재선택 안내를 확인함. 시험 앱의 instrumentation이 앱에서 취득한 해당 시험 파일의 지속 권한을 해제한 결과이며 권한 제공자별 자연 만료 방식 전체를 재현한 것은 아님.
- Android 15 에뮬레이터에서 AES-128, AES-256, RC4-128, RC4-40으로 만든 시험 PDF의 잘못된 비밀번호 안내와 올바른 비밀번호 열기를 확인함. AES-256 외 세 방식은 추가 시험한 결과임. Android 10~14의 암호 PDF 지원을 의미하지 않음.
- [rhwp 공개 암호 표본](https://github.com/edwardkim/rhwp/tree/v0.9.0/samples)의 HWP3, HWP5, HWPX 각 1개에서 비밀번호 오류 안내와 올바른 비밀번호 입력 후 첫 쪽 표시를 확인함. 모든 암호 방식과 문서 내용의 일치 여부는 미검증 상태임.
- [공개 Office 암호 표본](https://github.com/wilson-anysphere/formula/blob/main/fixtures/encrypted/ooxml/README.md) 중 소형 Agile 및 Standard 4.2 XLSX는 비밀번호 오류 안내 후 열림을 확인함. Standard 3.2 AES 표본은 PC Excel에서 읽기 전용으로 열렸으나 에뮬레이터에서는 암호 입력창 없이 로딩 상태가 지속됨. Standard RC4 표본은 PC Excel에서도 손상 오류가 발생해 앱의 해당 암호 방식 지원 여부를 판단할 수 없음. 모두 각 방식의 단일 표본이며 실기기는 미검증 상태임.
- Standard 3.2 표본을 닫은 뒤 멈춘 Office 엔진 때문에 다른 Office 파일도 열리지 않는 문제가 재현됨. 20초 동안 암호 입력창이나 결과 없이 열기가 진행되면 뒤로 닫을 수 있다는 안내를 표시함. Office 화면이 종료되면 정리 작업이 막힌 경우에도 별도 Office 프로세스를 종료하도록 보완함. 에뮬레이터에서 종료 후 1초 대기한 뒤 다른 암호 문서의 암호 입력창을 확인함. 해당 표본 자체의 열기 문제와 더 빠른 재열기 조건은 미해결·미검증 상태임.
- 해당 Excel의 암호 정보는 Standard 3.2이나 파일의 OLE 복합 저장 구조가 4096바이트 섹터를 사용하는 버전 4임. 같은 암호 데이터와 버전 3.2를 512바이트 섹터 구조로 구성한 비교 파일에서는 잘못된 비밀번호 안내와 올바른 비밀번호 입력 후 열림을 확인함. 문서의 DataSpaces 이름을 변경한 512바이트 구조도 열려 암호 버전 자체 또는 DataSpaces 부재만으로 멈춤이 설명되지 않음.
- 현재 포함된 LibreOffice 소스의 `sot/source/sdstor/stgelem.cxx`의 `StgHeader::Check`는 저장 구조 버전 3과 512바이트 섹터를 요구함. 해당 버전 4 표본은 기존 로딩이 멈췄으므로 버전 4와 4096바이트 섹터를 확인하면 엔진을 호출하지 않고 지원하지 않는 저장 방식으로 안내함. 내용을 확인창에 표시해 좁은 화면에서도 읽을 수 있도록 함. 이는 파일 열기를 구현한 것이 아니며 다른 버전 4 문서와 실기기 검증은 남아 있음.
- 약 171MiB 공개 PowerPoint를 시스템 선택기로 열고 6번 슬라이드에서 강제 종료한 뒤 최근 문서로 다시 열어 위치 복원을 확인함. 이는 에뮬레이터의 한 표본으로 실기기 속도·최대 메모리 또는 모든 대형 문서에 대한 결과는 아님.

## PDF·Office 선명도와 넘김 보완

- PDF와 Office 문서의 렌더링 너비를 기존 고정 960픽셀에서 실제 표시 영역에 맞춰 조정함. 페이지당 최대 2560픽셀과 약 419만 픽셀로 제한하며 PDF 페이지 캐시는 24MiB로 제한함. PDF는 확대·창 크기 변경에 맞는 해상도를 별도로 캐시함. PDF의 고배율에서는 제한에 따라 화면을 확대하면서 다시 흐려질 수 있어 타일 렌더링 검토가 필요함.
- PDF의 연속·한쪽·두쪽 보기와 PowerPoint의 기본 배율에서 좌우 밀기로 페이지·슬라이드 이동을 추가함. 확대 상태에서는 좌우 드래그로 확대 영역 이동을 우선함. 에뮬레이터에서 양방향 넘김, 두쪽 연속 이동 및 확대 상태의 페이지 유지 여부를 확인함.
- 같은 PDF와 PPTX 첫 화면을 실제 캡처 크기 1600×1920인 에뮬레이터에서 변경 전후 비교해 글자 윤곽 개선을 육안 확인함. 한 번의 화면 표시 후 단일 시점 PSS는 PDF 주 프로세스 82,452→102,177KiB, PPT Office 프로세스 394,258→401,295KiB로 측정됨. 독립 실행의 단일 측정이며 최대 메모리·속도 또는 실기기 성능을 의미하지 않음.
- Excel 핀치 확대 실패에 대한 사용자 제보는 별도 원인 분석과 실기기 검증이 필요함. PDF·한글·Word·Excel·PPT·CSV의 공통 확대 계획은 `docs/DESIGN.md`에 기록함.

## 코드 리뷰 후 보기 안정화

- 한쪽 보기의 100%와 확대 상태 사이에 페이지 높이 계산이 불연속적으로 바뀌던 PDF·Office 경로를 수정함. PDF 시험 문서의 색상 도형은 작은 핀치 후 너비가 64픽셀에서 68픽셀로 증가했으며, 별도 핀치 중심 시험도 통과함. 한정된 에뮬레이터 화면과 합성 문서의 결과임.
- 한글 검색 중 키보드 표시로 창 높이가 줄어든 상태의 페이지 크기가 유지되던 문제를 수정함. 창 크기 변경 시 한쪽 페이지를 다시 맞추고 검색 대상 페이지가 이전 화면에 덮이지 않도록 처리함. 에뮬레이터에서 본문·표 검색 강조와 다음 결과 이동을 확인함.
- Office 자산은 임시 파일을 완성한 뒤 이름을 교체하고, 앱 업데이트 시 자산을 다시 복사한 다음 완료 상태를 기록하도록 변경함. 에뮬레이터에서 이전 자산을 변경한 뒤 앱 업데이트와 문서 열기를 수행하여 자산 교체를 확인함. 복사 도중 강제 종료를 주입하는 시험은 아직 수행하지 않음.
- 최종 디버그 앱을 Galaxy Tab S10 Ultra에 설치하고 HWP·HWPX·PDF·DOCX·XLSX·CSV·PPTX 시험 파일을 열어 시작 화면으로 돌아가는 동작을 확인함. 태블릿에서 자동 스와이프는 페이지와 화면 버튼 모두에 반응하지 않았으며, 두 손가락 자동 입력 도구는 종료 코드 137로 중단됨. 실기기 손가락 제스처의 성공 여부를 해당 자동 시험으로 판단할 수 없음.

## 표시·암호 문제 재검토

- HWP 공개 표본의 차트 색상 차이를 렌더러 출력으로 다시 재현함. 차트는 테마 색상 참조를 사용하고 현재 엔진은 고정 근사 색상표로 해석함. 단일 표본에 맞춘 고정 색상 보정은 다른 문서의 색상을 훼손할 수 있어 적용하지 않음. 차트 원본 테마의 신뢰할 수 있는 해석과 다양한 표본 검증이 필요함.
- 4096바이트 섹터를 사용하는 암호 Excel에서 지원되지 않는 저장 구조 안내를 확인함. 이후 512바이트 섹터 구조의 Standard 3.2 비교 문서에서 잘못된 비밀번호 안내와 올바른 비밀번호 입력 후 열기를 에뮬레이터에서 확인함. 4096바이트 구조 자체의 읽기 지원은 미구현 상태임.
- Word의 간헐적인 화살표 깨짐은 사용자가 이후 정상 표시를 확인한 상태이며 재현되지 않음. 원인과 수정 효과를 확정할 근거가 없어 글꼴 설정을 임의 변경하지 않음.

## CFB 버전 4 암호 Excel 읽기 시험

- LibreOffice 26.2.6.3의 CFB 헤더 검사에서 버전 4·4096바이트 섹터 조합을 허용하고 헤더 섹터 크기를 반영해 페이지 수를 계산하도록 수정함. 앱에서 해당 저장 구조를 일괄 차단하던 분기를 제거함.
- Android 15 x86_64 에뮬레이터의 ARM64 변환 실행에서 4096바이트 구조의 Standard 3.2 공개 Excel 1개와 동일 암호 데이터의 512바이트 구조 비교 파일을 시험함. 각각 잘못된 비밀번호 안내와 올바른 비밀번호 입력 후 열기를 확인했으며, 원본 표본의 첫 시트에 `1 Hello`가 표시됨을 육안 확인함.
- 공개 Agile 암호 Excel과 별도 암호 Word·Excel·PowerPoint의 비밀번호 오류 및 열기를 확인함. 손상 Word·Excel과 외부 파일 권한 거부 안내, 일반 Word·Excel의 페이지·시트·확대 상태 복원도 확인함.
- 수정 LibreOffice ARM64 무서명 APK는 87,582,374바이트이며 SHA-256은 `bb60e326b39a67feb0459a790cf3d496113e8a999f728ab7dd543598e9e82f18`임. 정리 빌드한 MIN VIEWER ARM64 디버그 APK는 103,397,355바이트임. 압축 APK 기준이며 설치 크기와 메모리는 측정하지 않음.
- 4096바이트 구조의 다른 파일, 여러 암호 방식·복잡한 내용·손상 구조 및 실기기 동작은 미검증 상태임. CFB 버전 4를 사용하는 모든 Office 문서의 호환성을 보장하지 않음.

## 가로·세로 회전 확인

- Android 15 에뮬레이터에서 공개 HWP와 시험 PDF를 각각 2쪽으로 이동한 뒤 세로에서 가로로, 다시 세로로 회전함. 두 문서 모두 2쪽 위치가 유지됨을 확인함.
- 좁은 가로 화면에서 문서의 일부만 표시되며 나머지는 스크롤이 필요함. Office·CSV 회전, 확대 상태의 정확한 유지, 실제 갤럭시 기기와 분할 화면은 이번 시험 범위에 포함되지 않음.
